## Detection

Strong signals:

- `package.json` with `"@sencha/ext"` or `"extjs"` (very old apps may not have package.json at all)
- `Ext.define('My.app.SomeView', {...})` class-definition calls in JavaScript files
- `app.json` (Sencha Cmd build config) at repo root
- `Ext.application({...})` bootstrap call

Weak signals:

- `bootstrap.js` / `bootstrap.css` generated by Sencha Cmd
- Use of `Ext.create('Ext.grid.Panel', {...})`, `Ext.MessageBox`, `Ext.window.Window`
- `app/view/`, `app/controller/`, `app/store/` MVC directory layout (Sencha convention)

## Entry-point heuristic

Each `Ext.define(...)` call defining a view class (extends `Ext.panel.Panel`, `Ext.window.Window`, `Ext.grid.Panel`, etc.) is one entry point. Unit `id` = the class name's last segment (e.g., `My.app.OrderGrid` → `OrderGrid`); `kind = "component"`. Include the controller and store referenced by the view.

## Recommended target

`react-vite-ts` with a data-grid component library (AG Grid, Material-UI DataGrid, TanStack Table) — ExtJS apps are typically data-grid-heavy and a strong grid library is essential. Less commonly `angular` (similar opinionated structure).

ExtJS migrations are typically **slow** — the framework's tight coupling between view, controller, store, and model means component decomposition takes more passes than in plainer legacy JS apps.
